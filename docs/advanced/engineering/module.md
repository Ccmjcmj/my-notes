# 📚 模块化

解决 JS、CSS 文件拆分、依赖管理问题
（本文介绍前端模块化作为工程化的基础前提。）


## 模块化概念

把前端从 “写页面、复制粘贴 JS/CSS” 的手工干活，变成一套标准化、自动化、可维护的工业流程。
不是某个 API，而是一整套工具、规范、流程，覆盖项目从开发→校验→构建→打包→部署→维护全生命周期。

## 1：现在的前端框架都实现了模块化，我们写的代码默认就已经模块化了呀？为什么还要学？场景是什么？
**A：**
✅ 框架脚手架**帮你自动跑模块机制**，不用你手动配置 type="module"、不用手动处理加载顺序；
>
❌ 但**框架不会帮你做「合理的模块拆分、依赖设计、排坑」**，遇到问题、写底层工具、面试、性能优化的时候，不懂模块化底层就会卡壳。你现在的疑惑非常典型：

> “我新建一个 Vite/React/Vue 项目，直接新建 utils.js、直接 import，好像天然就能用，那我还专门学模块化干嘛？”

分成 3 层讲清楚：**日常开发场景、踩坑场景、进阶 / 面试场景**

#### 一、先分清两件事：「模块机制」和「模块设计」

1. **模块机制（ESM/CommonJS）**：JS 语言 / 打包工具提供的能力 —— 作用域隔离、导入导出、依赖解析。Vite、Webpack 已经**内置开启**，你开箱即用。
2. **模块设计**：怎么拆分文件、怎么组织导出、怎么控制依赖、规避循环依赖、按需加载。**框架不会替你做**。

👉 你现在能简单 import，只是**在享受模块化带来的红利**，不等于你懂它。
就像开车：汽车自带变速箱（相当于框架自带模块机制），你不用自己造变速箱；但你要懂换挡、路况什么时候减速，不然遇到特殊情况直接趴窝。

#### 二、什么时候就算框架自动模块化，你也必须懂？（真实工作高频场景）
>
###### 场景 1：出现诡异 BUG，看不懂根源（最常见）

举几个真实业务里经常遇到的：

1. **循环依赖**
a.js 引入 b.js，b.js 又引入 a.js。
   - ESM 和 CommonJS 的表现完全不一样！
   - 框架不会报错，只会导出 `undefined`，数据莫名丢失，你如果不懂模块加载机制，根本排查不出来。
2. **Tree-Shaking 不生效，打包体积莫名很大**
你以为没用到的代码会自动删掉，但如果你写成 CommonJS 导出、或者导出写法不对，Tree-Shaking 直接失效。

> 很多初级开发遇到包体积过大，不知道根源就是模块规范问题。
3. **变量莫名被污染 / 单例缓存问题**

模块**会被缓存**，同一个模块多次 import，拿到的是同一份实例。
很多人写公共 store、工具对象踩坑：以为每次 import 都会新建对象，结果数据全局串了。

> 这个是模块底层特性，框架完全不会提醒你。

###### 场景 2：脱离框架写代码的时候（非常多）

不是所有前端代码都写在 Vue/React 业务项目里：

- 写原生 JS 工具、公共 SDK、埋点脚本、浏览器油猴脚本、简单 H5 活动页
- 写 Node 脚本（爬虫、文件处理、CI 脚本）
- 封装通用组件库、工具包（npm 包）
👉 这些场景**没有 Vite/Vue 帮你兜底**，需要你自己选择模块规范、处理导出。

###### 场景 3：性能优化：动态导入 import () 做懒加载

路由懒加载、大弹窗 / 大图表按需加载，核心就是 ESM 的**动态导入**。

```
// 动态导入，运行时才加载，减少首屏包体积
const Chart = await import('./BigChart.js')
```

框架路由懒加载底层就是封装了这个 API。
**只会复制现成路由配置，不懂原理，就没法自定义按需加载逻辑。**

###### 场景 4：工程化、打包配置、迁移项目

比如：

- 老 jQuery / 老 Webpack 老项目迁移到 Vite
- 配置打包 externals、分包策略
- monorepo 多包管理（中大型项目）
打包工具的配置项本质全是围绕**模块解析规则**设计的，不懂 ESM 和 CJS 差异，配置根本看不懂。

###### 场景 5：面试硬性考点（求职刚需）

面试官很喜欢问：

> 
> Vite 默认是什么模块？ESM 和 CommonJS 区别？循环依赖表现？Tree-Shaking 条件？`import()`和普通 import 区别？
> 很多天天写 Vue/React 的初级开发，这里直接哑口无言。
> 面试官的潜台词：**你是只会调用框架，还是理解底层原理，有排查复杂问题的能力？**

#### 三、区分两种人的区别（很现实）

✅ **只会用框架的初级（瓶颈很快到来）**

- 知道可以新建 utils，import 引入函数
- 遇到循环依赖、打包体积、模块缓存问题 → 束手无策，只能等别人帮忙
- 只能做简单业务页面，很难参与公共工具、组件库、工程化相关工作

✅ **懂模块化的初级（能稳步往中高级走）**

- 不仅会 import，清楚 ESM 是**静态编译**，CommonJS 是**运行时动态**
- 能规避循环依赖、知道 Tree-Shaking 的前提
- 能独立封装公共工具包、做懒加载优化、排查打包异常

#### 四、给你一个极简学习定位（适配你现阶段）

**不用一开始深挖底层加载源码，优先掌握 “框架里会踩坑的知识点”**
重点清单：

1. ESM `import / export` 静态特性（编译时解析，不能写在 if 里）
2. CommonJS `require/module.exports` 和 ESM 核心差异
3. 模块缓存现象
4. 循环依赖现象
5. `import()` 动态导入（懒加载）
6. Tree-Shaking 生效条件

> 不是让你脱离框架手写 type="module" 项目，而是**理解框架背后这套机制，解决框架解决不了的疑难问题**

#### 五、一句话总结

框架给你搭好了模块化的环境，**免去了你最繁琐的基础配置**；
但**BUG 排查、性能优化、封装底层工具、跨环境开发、面试**，都依赖你理解模块化本身。
只会 “框架自动 import” 属于**黑盒使用**；懂模块化，才是**白盒可控**。

## 2：Webpack 是在 ESM 普及之前，帮我们把各种模块打包给浏览器执行，那现在esm普及之后岂不是没用了？
**A：** ✅没错，现在主流浏览器原生支持 ESM 了，Webpack 打包的用处确实少了。
**ESM 普及 ≠ Webpack 立刻淘汰，只是它的核心价值变了；但现在大量存量项目、复杂工程场景依然离不开它，只是新项目很多优先选 Vite/Rollup。**
关键误区：浏览器原生 ESM 只解决了「模块能跑」，**没有解决工程里一大堆配套问题**。Webpack 不只是 “把模块转成浏览器能认的代码”，它是一套完整的**前端应用构建系统**。
#### 一、先搞清楚：原生 ESM 本身有哪些短板（就算现在浏览器全支持，依然存在）

原生 ESM 能干的事：`import/export`、隔离作用域。
但是原生 ESM 做不到 / 很难做：

1. **不识别非 JS 资源**
你直接 `import './index.css'`、`import logo from './logo.png'`、`import .vue/.tsx`，**浏览器原生 ESM 直接报错**。
浏览器只认 js/mjs，css、图片、vue 单文件、ts、sass 都不是标准 JS 模块，原生不支持。
2. **没有自动 polyfill、语法转译**
你写的 ESNext、TS 新语法，低版本浏览器不认识；原生 ESM 不会自动转成兼容代码。
3. **没有开箱即用的资源压缩、Tree-Shaking、代码分割、缓存策略**
原生 ESM 可以用`import()`懒加载，但**不会自动优化打包产物、自动生成 chunk、自动给文件加 hash 做长期缓存**（线上性能必备）。
4. **裸模块标识符无法解析**
你写 `import React from 'react'`，浏览器原生 ESM 根本不知道去哪里找 node_modules 里的 react 包！
> 
> 浏览器只能识别**相对 / 绝对路径**，不识别裸包名，这是巨大痛点。
> 👉 Vite / Webpack / Rollup 都要自己实现**模块解析逻辑**，去 node_modules 查找依赖。
5. **缺少灵活的扩展能力**
比如注入全局变量、自动注入环境变量、自动生成 html、静态资源拷贝、mock、代理、自定义编译逻辑等，原生 ESM 完全没有。

> 
> 简单概括：**原生 ESM 解决「模块标准」，不解决「前端工程化」**

#### 二、那 Webpack 现在还有什么不可替代的场景？

###### ✅ 场景 1：海量存量老项目（最主要原因）

国内大量企业项目、中台、老管理系统，都是早年 Webpack 搭建的，重构迁移成本极高。
很多公司不会无缘无故把稳定跑了多年的 Webpack 项目改成 Vite。**存量市场巨大，面试高频出现。**

###### ✅ 场景 2：极度复杂、高度定制化构建流程

Webpack 的 Loader + Plugin 生态是最成熟、最庞大的。
很多定制需求：

- 自定义文件编译、复杂代码注入
- 精细的分包策略、动态公共 chunk 拆分
- 复杂微前端、qiankun/module federation（模块联邦，多应用共享代码）

> 
> Module Federation 是 Webpack 标志性能力，早年 Vite 对它兼容成本很高，复杂微前端很多团队依然选 Webpack。

###### ✅ 场景 3：多端、混合复杂工程

一些老的 Electron、混合 APP、多页面 MPA 复杂项目，很多团队习惯 Webpack 成熟的配置方案。

##### 三、什么时候 Webpack 不再优先推荐？

**全新起步的业务项目（Vue/React 普通后台、H5）**
现在行业主流选择：**Vite**
原因：开发环境基于原生 ESM，不用全量打包，启动、热更新速度碾压 Webpack。
生产环境 Vite 底层默认用 Rollup 打包。

> 
> Rollup 和 Webpack 定位区别补充：
> Rollup 更适合**库打包**（组件库、SDK、npm 包），输出干净的 ESM/CJS；
> Webpack 更偏向**应用打包**（完整业务项目），擅长处理各类静态资源、复杂分包。

##### 四、一条清晰的演进时间线，帮你理顺逻辑

1. **很早之前**：浏览器没有任何模块能力 → 只能全局 script，AMD/require.js 尝试补模块化
2. **ES6 出 ESM 标准，但浏览器支持很差** → Webpack 崛起：把 CJS/AMD/ESM 全部打包成浏览器能跑的单 JS
3. **近几年，现代浏览器全面支持原生 ESM**
→ 新工具 Vite 诞生：dev 直接复用浏览器原生 ESM，抛弃 Webpack 前置全量打包的慢模式
4. **当下现状**
   - 新项目：优先 Vite
   - 老项目、微前端模块联邦、高度自定义工程：大量继续 Webpack
   - 写组件库 / 工具包：Rollup

#### 五、回到你学习的角度（你是初级前端）

你不用死磕 Webpack 各种复杂 loader/plugin 配置，但是**必须了解 Webpack 核心思想**，理由：

1. 面试一定会问 Webpack 和 Vite 区别、打包原理；
2. 进公司大概率会维护 Webpack 存量项目；
3. 理解 Webpack，你才能真正分清：**原生 ESM、模块解析、loader、bundle、chunk**这些工程核心概念，不然 Vite 你也只会黑盒使用。

##### 极简总结

ESM 只是语言层面的模块规范，**它 ≠ 前端工程化**。
Webpack 的本职从来不是 “转模块语法”，而是**管理整个前端资源、依赖、编译、打包、优化**。
ESM 普及只是削弱了 Webpack 当年最核心的刚需，但**工程配套能力、存量项目、微前端场景**让它至今没有消失，只是不再是新项目第一选择。
